# 插件在手机端的分级方案

> **Status**：设计定稿
> **日期**：2026-11-16
> **适用范围**：所有希望插件在 DSH Pocket iOS 里被打开的作者

## 为什么需要分级

DSH 的核心是插件。手机上能不能用好 DSH，取决于能不能用好插件。

但插件作者对移动端的投入意愿差别很大：

- 有人只想「装上就能用」，不想为手机多写一行
- 有人愿意专门做移动页面，但只熟悉 Web
- 有人愿意为最好的体验学一套声明式协议

**一套要求统一投入的协议会把前两类作者挡在外面。**

所以按投入递增、收益递增分三级，作者自己选。

## 三级方案

| 级别 | 作者要做的 | 手机上的样子 | 学习成本 |
| --- | --- | --- | --- |
| **L0** 什么都不做 | 不声明 `dsh.mobile` | 列表里可见，**没有「打开」按钮** | 0 |
| **L1** 写移动页面 | `kind: "web"` + 一个 HTML 页面 | WebView 打开它 | 会 HTML |
| **L2** 声明式原生 | `kind: "native"` + JSON schema | App 用 SwiftUI 原生渲染 | 学一套 JSON 结构 |

### L0：不声明

```json
// package.json 里没有 dsh.mobile
```

**表现**：插件出现在手机列表里，能开关，但**没有「打开」入口**。

**当前表现**：列表里可见、能开关，但没有「打开」入口（`canOpen` 由有没有 `mobilePath` 决定）。

#### 关于「能不能自动勾住桌面端 UI」——先给结论：**能做到，但还没验证值不值得**

曾经这里写的是「技术上做不到」。**那个判断是错的**，2026-11-16 查证后修正。

查证到的事实：

| 项 | 事实 | 含义 |
| --- | --- | --- |
| CSS 类名 | 语义化的 `dsh-sidebar-width`、`dsh-dockkit-*`，**不是哈希** | 覆盖样式不会随构建失效 |
| 布局控制 | CSS 变量 `--dsh-chat-content-width`、`--dsh-sidebar-*` | 可以收窄/隐藏区域 |
| 右侧栏状态 | `localStorage["dsh.sidebar-right.v1"]`，**key 稳定** | 可以预设选中的面板 |
| 状态结构 | `{ bySession: { [sessionId]: { layout: { activeTabId } } } }` | **按会话存**，需要会话上下文 |

所以理论上可以：App 先取最近会话的 id → 注入 localStorage 预设 `activeTabId`
→ 注入 CSS 收紧布局 → 加载 DSH Web → 只显示那个插件面板。

**真实代价**（不是"做不到"，是"代价是否值得"）：

1. 为看一个面板要加载整个 DSH Web（React + 全部 client bundle）
2. 需要处理时序：localStorage 必须在首次渲染前就位，右侧栏要等会话加载完才出来
3. 桌面交互逻辑（hover、右键菜单、拖拽）在手机上不适用，观感未知

**状态**：待实验验证（勾住 DSH Web 只显示一个插件面板，用截图判断观感）。
实验结论出来前，L0 保持「列表可见、无打开入口」。

### L1：Web 页面

```json
"dsh": {
  "mobile": {
    "version": 1,
    "kind": "web",
    "title": "音频解析",
    "path": "/dsh-audio-parse/mobile"
  }
}
```

插件自己提供一个路由，返回 HTML。手机上用 `WKWebView` 加载。

**优点**：完全自由，想画什么画什么。
**上限**：WebView 的天花板 —— 滚动不如原生跟手、没有原生长按菜单、拿不到分享/相册/震动。

**参考实现**：见本仓库 `spec/2026-11-16-0600-plugin-mobile-protocol.md`，
以及 `dsh-plugin-panel` 仓库里的 `templates/mobile-plugin/`。

### L2：原生渲染

**L2 必须拆成两半**——它们的成本差一个量级，混在一起会误判。

#### L2a：配置表单 —— **DSH 已经提供完整接口，作者零投入**

DSH 的 `settings` 服务本来就是「按插件 Config schema 生成表单」的，
而且官方明确在等客户端来实现它（见下面的原话）。

```
插件写 Config schema（写插件时的标准做法，不用为手机改任何东西）
    ↓
手机调 settings.describe()  → schema + 当前值 + 修订号
    ↓
SwiftUI 按 schema 生成原生表单
    ↓
settings.mutate() 提交（带修订号，防并发覆盖）
```

**接口（`packages/settings/settings/src/index.ts`，已核对源码）**：

```ts
describe(options?): SettingsDescriptor[]          // 注意：同步
update(ns, patch, expectedRevision?): Promise<void>
mutate(ns, ops, expectedRevision?): Promise<void>

interface SettingsDescriptor {
  ns: string          // profile 条目 id
  autoGenerate: boolean  // 是否允许客户端按 schema 生成页面
  schema: unknown     // schemastery 的 toJSON()
  value: unknown      // 当前值
  revision: number    // 乐观锁
  base?: unknown      // 继承层
  user?: unknown      // profile 覆盖
  applies: 'live'
  secrets?: RedactedSecret[]   // 秘密值只给存在性标记，从不返回明文
}
```

**DSH 官方原话**（`packages/settings/settings/README.zh.md` 第 39 行）：

> 每个表单报告 `autoGenerate`（默认开启，**供按 schema 生成页面的客户端使用**）；
> **目前没有已发布的客户端这样做**。

**schema 是 schemastery 格式**（JSON Schema 的变体，字段挂在 `dict` / `inner` / `list` 下）：

```js
{ "type": "object", "dict": { "port": { "type": "number", "meta": { "default": 3091 } } } }
```

渲染映射很直接：

| schemastery 类型 | SwiftUI 控件 |
| --- | --- |
| `string` | `TextField` |
| `number` | `TextField(.numberPad)` / `Stepper` |
| `boolean` | `Toggle` |
| `union` / `const` | `Picker` |
| `object` | 分组 `Section` |
| `array` | 列表 + 增删 |

**限制**（源码与文档都已确认）：

- 只显示 **`.volatile()` 声明的字段** —— 非 volatile 的配置改了要重挂插件
- 嵌套 Include 独立拥有配置，不能从当前 profile 的表单编辑
- 秘密值（`role: 'secret'`）只返回存在性标记

**结论：技术上 L2a 是「中等工程」，不是「重工程」**——接口齐全、作者零投入。

#### ⚠️ 但有一个警示：还没人做，可能不只是因为没人想到

2026-11-16 读了同类项目 Whaleness（794 stars、MIT、iOS+Android 双端、315 MB 源码）的实现：
**它也没做配置表单编辑**。`PluginsView.swift` 里的 `componentField` 是只读展示：

```swift
private func componentField(_ title: String, value: String) -> some View {
    VStack { Text(title); Text(value).textSelection(.enabled) }   // 只能选中复制
}
```

而且有 `readOnlyReason`（不可修改原因）字段。

DSH 官方说「目前没有已发布的客户端这样做」——现在证实**连做得最成熟的客户端也没做**。

**所以 L2a 的优先级应当下调**，先验证需求再投入。可能的原因：

- 需求不强烈：插件配置在手机上改的场景本来就少
- 或者成本被低估：schemastery → SwiftUI 的映射有坑（`union` 嵌套、`array` 增删、条件字段显隐）

**在拿到真实需求前，别把 L2a 当「性价比最高的下一步」。**

#### L2b：内容展示 —— 才需要自建 UI DSL

L2a 只管「配置」。插件要在手机上**展示自己的内容**（比如音频解析的图片列表、
节奏档案的图表），仍然需要另一条路：

```json
{
  "tabs": [
    { "title": "图片", "count": "{{images.length}}",
      "content": { "type": "grid", "source": "images",
                   "item": { "type": "image", "src": "{{url}}", "caption": "{{title}}" } } }
  ],
  "data": { "images": { "command": "list-assets", "args": { "kind": "image" } } }
}
```

**这部分仍是重工程**：DSL 要设计、渲染器要写、数据绑定要定，
而且设计错了会返工。**所以放在最后，且先用 L1.5 换真实反馈。**

> **对先前判断的修正**：这份文档早先把 L2 整体估成「要设计一整套 UI DSL」，
> 那个估计只对 L2b 成立。L2a 的正确做法是复用 DSH 已有的 settings schema，
> 不用自己造。

## 一个中间档：L1.5（JS Bridge）

在 L1 和 L2 之间还有一个低成本选项，**建议先于 L2 落地**：

```
L1.5  kind: web + JS Bridge
      插件继续写 HTML，但页面里能调：
        native.share({ text, url })
        native.saveImage(src)
        native.haptic("light")
        native.openURL(url)
```

| | L1.5 JS Bridge | L2a 配置表单 | L2b 内容展示 |
| --- | --- | --- | --- |
| 作者要学新东西 | **0**（还是写 JS） | **0**（已有 config schema） | 要学一套 DSL |
| 现有插件能否立刻受益 | ✅ 加几行就行 | ✅ 只要声明了 volatile 配置 | ❌ 要重写页面 |
| 解决体验天花板 | 部分（原生能力 + 手势） | 不涉及（只管配置） | 完全 |
| 实现工作量 | 小 | **中等** | 大 |

**三者解决的是不同问题，不互相替代**：

```
L2a  插件参数填不了       → 手机上有原生表单
L1.5 页面想要原生能力     → 插件页里能调 share/haptic
L2b  页面本身要原生体验   → 内容和 App 一样顺滑
```

**L1.5 还能指导 L2b 的设计**：先看插件最常调哪些原生能力，再决定 DSL 里要不要内置。

## 路线与取舍

**产品定位**：

```
核心：iOS 体验
重心：让插件在 iOS 上完美体现
理由：插件是 DSH 的核心
```

**这意味着不追求「通用客户端的完整功能列表」**，
而是把资源集中在：插件列表、插件页面、插件调原生这三件事上。

**落地顺序**：

```
第 0 步  基础体验债（都是一两行的改动）
         视频内联、深色模式、文本大小
         ↑ 不清掉，L1 的页面再好看也显得糙

第 1 步  L1.5 JS Bridge
         ↑ 现有插件不加学习成本就能受益，是确定性收益

第 2 步  L2a 配置表单（先验证需求）
         ↑ 接口齐全、作者零投入，但连 794 stars 的成熟客户端都没做，
           先用真实场景确认「手机上改插件配置」是否真有需要

第 2 步  L2 原型
         先只支持 list / grid / image / text 四种
         ↑ 验证 schema 是否真的好用，再生产完整渲染器
```

**为什么 L2 放最后**：schema 设计错了会返工，而返工成本远高于先拿 JS Bridge 换取真实反馈。
DSH 内核**没有对外的插件列表 API**（`/plugins/*` 只是 client 资源路由），
所以聚合能力由宿主插件提供（见 `spec/2026-11-16-1420-mobile-plugin-aggregator.md`）。
