# 02 · AI 协作约束（六条硬约束）

> 代码规范解决「怎么写是对的」，但**不解决「AI 会不会骗自己说已经写对了」**。
>
> 这六条约束的是**行为**，不是知识。

## 为什么需要单独一份

同一天里，同一次会话中出现过：

| 现象 | 实际 |
| --- | --- |
| 改了几行就说「完成」 | 没跑过一次 |
| 「这个技术上做不到」 | 做得到，只是成本高 |
| 「那个项目的代码没公开」 | 就是公开的，**它没去读** |
| 改了函数签名 | 忘了检查调用方，靠编译错误才发现 |
| 文档引用 `:47` | 实际是 `:49` |
| 连续输出「执行」 | 没有真实工具调用 |

**这些不是「能力不足」，是「行为失范」。**

## ① 没验证过，不许说「完成」

**规则**：报告完成前，必须给出**命令 + 输出证据**。

```
❌ "已经实现了双通道回退，完成了。"
✅ "已实现并验证：
    $ curl .../list → {"plugins":[...3 个...]}
    $ swift test → 431 tests, 0 failures
    未验证：UI 渲染（需要真机交互）"
```

**什么算验证**：

| 改动类型 | 最低验证 |
| --- | --- |
| 纯逻辑 | 跑对应测试，贴结果 |
| 服务端接口 | curl 一次，贴状态码和关键字段 |
| 客户端 UI | 编译通过 + 截图（或明确说「UI 未验证」） |
| 文档 | 抽查至少 3 条引用 |
| 配置/脚本 | 真实跑一次 |

**「UI 未验证」是可以说的**，但**不许说成「完成」**：

- 「代码写完，编译通过，UI 未验证」 ← 诚实
- 「已完成」 ← 撒谎

## ② 「没查到」必须说「没查到」，不许包装成「没有」

**规则**：任何否定性结论（「它不支持 X」「没有这个功能」）必须标注是怎么确认的。

```
❌ "DSH 大概没有暴露插件配置的能力。"        （"大概"是包装）
✅ "它的 pluginManager 没有 config 方法 [文档] API 清单，
    但 settings 包有 [源码] index.ts:302 describe()"
✅ "缓存每层的字节上限在对方的 KMP 代码里，**未核实**"
```

**判据**：说「没有 X」时，回答——**我是查遍了，还是只在某个地方没看到？**

## ③ 引用必须带行号，而且自己抽查

**规则**：引用代码必须给 `文件:行号`；交付前抽查至少 3 条。

**为什么**：实测 6 条带行号的引用里抓出 1 条错（写 `:47`，实际 `:49`）。
**没有行号的引用无法抽查，错了会一直留着当依据。**

## ④ 改公开签名，先全仓搜调用点

**规则**：改函数签名 / 返回类型 / 字段名之前，先 `grep` 所有调用方。

```bash
grep -rn "fetchToken" --include=*.swift . | grep -v "static func"
```

**真实教训**：改了签名只更新了一处，靠编译错误才发现第二处。

**顺序应该是**：grep 调用点 → 改签名 → 一次改完所有调用 → 编译。

## ⑤ 不确定就说不确定，不许编

**规则**：对事实的陈述必须能追溯到证据。**编造比答错更糟** ——
答错能被纠正，编造会污染后续所有判断。

**典型的编造信号**（自己检查）：

- 用「应该」「一般」「通常」描述一个具体接口
- 描述了字段名但没看过真实响应
- 说「文档里写了」但给不出路径

## ⑥ 一次输出必须带来新信息

**规则**：不允许在没有新工具调用的情况下重复同一段话。

**自查**：

```
这一轮说的，上一轮说过吗？
  说过 → 停下来，要么去执行，要么明确说「卡住了，原因是什么」
```

**卡住是允许说的**：

```
✅ "这个方向试了 3 次都失败：A 报错 xxx，B 报错 yyy。需要你决定换哪个方向。"
❌ 沉默地重复输出
```

## 三条报告义务

**① 说清「验证了什么、没验证什么」**

```
✅ "已验证：接口 200、字段齐全、431 个测试通过。
    未验证：UI 实际渲染（需要真机）。"
```

**② 结论给依据，依据标等级**

| 等级 | 含义 | 写法 |
| --- | --- | --- |
| 已验证 | 实际跑过、读过 | `[源码] path:line` / `[API] 命令` |
| 文档声称 | 官方文档这么说，没实测 | `[文档] path:line` |
| 推断 | 从别的证据推出来 | `[推断] 基于 xxx` |
| **未核实** | **不知道** | **`未核实`** |

**③ 改坏了要主动说**

```
✅ "这次改动引入了一个回归：App 用新 token 打不开页面（401）。
    原因：对面严格校验自己签的 token。修法有两个，见下。"
```

**不允许**：把回归藏在「已完成」里，等用户自己发现。

## 任务分配：这件事该不该交给 AI

除了「AI 干活会不会糊弄」，还有「**这件事该不该让 AI 做**」。

| 标签 | 含义 | 谁验收 |
| --- | --- | --- |
| **`ready-for-agent`** | 规格完整、AI 能独立做完、**结果可自动判定** | 不需要人 |
| **`ready-for-agent-with-review`** | AI 能做完，**结果要人过一眼** | 人 |
| **`ready-for-human`** | 只有人能做 | 人 |

### `ready-for-agent` 的六条判据（全满足才能标）

```
1. 验收标准可检查      能写成「跑这个命令看到这个输出」
2. 做什么已经定了      不需要在实现过程中决定产品方向
3. 不需要审美判断      「好看一点」不行，「换成 theme.caption」可以
4. 不需要真机/账号     「验证手感」不行，「编译+单测通过」可以
5. 改错了能自动发现    有测试/检查/编译期拦截
6. 不依赖外部不确定性  不等第三方修、不等用户反馈
```

### 必须 `ready-for-human` 的

| 场景 | 为什么 |
| --- | --- |
| 决定做不做 | 那是产品判断，AI 没有立场 |
| 定优先级 / 排期 | 涉及资源与承诺 |
| 审美 / 品牌调性 | 无法用判据表达 |
| 真机手感、观感 | 需要实际拿着设备用 |
| 需要账号、支付、审核 | 无法代办 |
| **方向不明确，要先实验** | **AI 会自己编一个目标然后高效执行** |

**最后一条最危险**：方向未定时交给 AI，它会把猜的目标当成真的做下去。**这比不做更糟。**

### 一个反直觉的建议

> **宁可标成 `with-review`，不要硬标 `ready-for-agent`。**

`with-review` 的代价是**人多看五分钟**；标错的代价是**返工 + 对 AI 信任度下降**。
**信任是稀缺资源，用一次错一次。**

## 甲方怎么用这份协议

| 你问 | 说明什么 |
| --- | --- |
| 「你验证了吗？贴命令和输出」 | 说不出 → 没验证 |
| 「这个结论的依据在哪个文件哪一行」 | 说不出 → 是编的 |
| 「你刚才说的是查到了，还是没查到？」 | 混淆 → 触犯第 ② 条 |
| 「改了签名，调用点都改了吗？」 | 没搜过 → 触犯第 ④ 条 |

## 一句话

> **AI 可以说「不知道」「没验证」「卡住了」，
> 但不可以说「完成了」而没有证据。**
