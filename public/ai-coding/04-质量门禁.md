# 04 · 质量门禁（让约束自动生效）

> 前面三份文档都是「约定」。**约定靠人记，就一定会忘。**
>
> 这一份把它们变成脚本：**跑一下，退出码不为 0 就是没过。**

## 为什么必须自动化

**真实对比**：

| 靠人记 | 靠脚本 |
| --- | --- |
| 「记得跑一下测试」 | `swift test` 在 CI 里，失败阻断合并 |
| 「记得别超过 400 行」 | `check-size.sh` 扫全仓，超了报错 |
| 「记得引用要带行号」 | 抽查 3 条，错了重写 |
| 「记得更新架构事实」 | `architecture-facts.sh` 生成，手改会被覆盖 |

**人的注意力是稀缺资源，脚本的不是。**

## 四类门禁

### ① 测试门禁

```bash
cd <CorePackage> && swift test    # 或 npm test / go test
```

**要求**：测试数量要**稳定**。今天 431 个，明天变成 42 个，说明测试文件被误删或被跳过。

```bash
# 把测试数记下来，下降就报警
swift test 2>&1 | tail -3 | grep -oE "[0-9]+ tests" 
```

**一个反直觉建议**：**不要追求覆盖率**。

覆盖率 80% 的项目里照样满是 bug —— 因为测的是「能跑」，不是「行为对」。
**先保住关键路径的行为测试，覆盖率自然会上去。**

### ② 架构门禁

```bash
./scripts/check-architecture.sh     # 退出码 1 = 有违规
```

检查三类东西：

| 类型 | 例子 |
| --- | --- |
| **依赖方向** | 纯逻辑层 import 了 UI 层（不该反过来也得查） |
| **文件规模** | 单文件超过该层阈值 |
| **假拆分** | 拆了 5 个 extension，其中 1 个还是 600 行 |

**阈值要分层，不能一刀切**：

| 层 | 建议上限 | 理由 |
| --- | --- | --- |
| 纯逻辑（可单测） | 400 | 短，才好测 |
| 编排层 | 600 | 天然比策略长 |
| UI | 不设硬限 | 用别的判据（见下） |

**一刀切的教训**：曾经统一 400 行，逼出一个 197 行的碎片 extension ——
改一个功能要跳四个文件，可读性反而下降。

**真正该管的是「一个文件干几件事」，不是行数。**

### ③ 事实门禁

架构数字（文件数、行数、依赖图）**必须脚本生成，禁止手写**。

```bash
./scripts/architecture-facts.sh   # 产出 docs/architecture/fact.json
```

**为什么**：手写的数字会过期。过期的事实比没有事实更糟 ——
它会让你基于错误的前提做判断。

**规则**：`fact.json` 顶部写明「本文件由脚本生成，手改会被覆盖」。

### ④ 引用门禁（人工抽查）

这个没法完全自动化，但可以**抽样**：

```bash
# 随机抽 3 条带行号的引用，人工核对
grep -rhoE '[a-zA-Z/]+\.(swift|ts|md):[0-9]+' docs/ | shuf -n 3
```

**实测**：6 条里抓出 1 条错（写 `:47`，实际 `:49`）。

**为什么值得**：错的行号比没有行号更危险 —— 它看起来是核实过的。

## 一个可用的最小门禁集

**别一次上全套。** 从这两条开始：

```bash
#!/usr/bin/env bash
# scripts/check.sh —— 提交前跑这个
set -e

echo "① 测试"
(cd DSHKit && swift test 2>&1 | tail -3)

echo "② 架构违规"
./scripts/check-architecture.sh

echo "✅ 全部通过"
```

**挂到 git hook**（可选但推荐）：

```bash
# .git/hooks/pre-commit
#!/bin/sh
exec ./scripts/check.sh
```

**注意**：pre-commit 太慢会让人用 `--no-verify` 绕过。
**控制在 30 秒内**，超过就移到 CI。

## 门禁和人的分工

| 谁 | 管什么 |
| --- | --- |
| **脚本** | 可判定的：编译、测试、文件规模、依赖方向、引用存在 |
| **人** | 不可判定的：命名是否准确、注释是否过时、设计是否合理 |

**不要把不可判定的东西硬塞进脚本** —— 那会产生大量误报，
然后所有人学会绕过它。

## 一个诚实的提醒

**门禁只能防止「已知的错」**，不能发现「没想到的错」。

它能保证：
- 代码能编译
- 测试能通过
- 没有违反你写下的规则

**它不能保证**：
- 这个功能是用户想要的
- 边界情况都考虑到了
- 三个月后还能维护

**所以门禁是下限，不是质量本身。**

## 一句话

> **能被脚本检查的，就不要靠自觉；
> 不能检查的，就诚实地说「这条靠人」。**
