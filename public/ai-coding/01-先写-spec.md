# 01 · 先写 spec，再写代码

> AI 编码最大的风险不是语法错误，是**漂移**：
> 一个需求在几千字上下文里被逐步放大、曲解、夹带私货。

spec 的价值在于：**在改动发生之前，把「做什么、不做什么、做完怎么验收」钉死成文字。**

## 什么时候要写

| 改动 | 要写 spec 吗 |
| --- | --- |
| 改一个 typo、调一个常量 | 不要 |
| 加一个字段、修一个明确的 bug | 写**三行版**（见下） |
| 新功能、改行为、动架构、跨多个文件 | **完整七段** |
| 重构 | 可挂靠已有架构文档，但必须满足「判据可机器验证 + 不改行为」 |

## 三行版（小改动用这个就够）

```markdown
改什么：<一句话>
不碰什么：<一句话，防止顺手改别的>
怎么算对：<一条能当场检查的标准>
```

**第二行最重要**。「不碰什么」写下来，AI 就不会顺手重构你的其他代码。

## 完整七段（新功能 / 改行为用）

```markdown
# <一句话说清这次要做什么>

Status: Draft | In Review | Accepted
预估工时: 60–90 分钟

## 1. 背景
为什么现在要做这个。写清触发它的具体问题，不要写「为了提升体验」这种空话。

## 2. 目标与非目标
目标：做完之后什么会变。
非目标：**这次明确不做什么**。这一栏防止范围膨胀，AI 和你自己都需要它。

## 3. 参考实现
看了哪个开源项目 / 哪段已有代码。抄了什么思路，不抄什么，为什么。

## 4. 方案
具体怎么做。关键决定要写「为什么这样做」和「为什么不那样做」。
**被否决的备选方案单独成段** —— 半年后没人记得你考虑过什么。

## 5. 测试计划
每个模块对应哪些测试，量化通过标准，**标注测试放在哪个 target / 目录**。
写不出 target 就说明它不可测 —— 当场改成「分层验证方式」，不要留到期后发现。

## 6. 风险与回滚
最可能出错的点、怎么验证、怎么回退。

## 7. 未决问题
还没定但不阻塞执行的项。不写就会丢失，或者在实现时临场发挥。
```

## 为什么要「非目标」这一栏

**实测**：不写非目标，AI 会做「它认为完整」的版本。

例如你说「加一个复制按钮」，它可能顺手加了：
- 复制成功提示
- 复制历史
- 长按菜单
- 分享到其他 App

这些都不是你要求的。**一行「非目标：不加分享、不做复制历史」，就能省掉一轮返工。**

## 为什么要「参考实现」

**没有它**：AI 会按自己的偏好选方案，而它的偏好和你不同。
**有它**：它知道「我们项目里同类问题是怎么解的」，产出和你现有代码风格一致。

写法：

```markdown
参考：<仓库>/<文件>:<行号>（看它如何用横向容器 + 最大宽度约束）
采用：横向滚动 + 宽度上限 2.2 倍
不采用：对方的隔行底色（与我们的分隔线叠加会变粗）
差异原因：我们的表格在消息气泡内，宽度上限按容器比例算
```

**带行号**。没有行号的引用无法核对，错了会一直留着当依据。

## 验收标准要「可检查」

| ❌ 不是验收标准 | ✅ 是验收标准 |
| --- | --- |
| 体验更好 | 首页加载 < 800ms |
| 代码更清晰 | 单文件 ≤ 400 行，脚本检查通过 |
| 修好了 | 断网 30 秒后恢复，消息不丢不重 |
| 支持深色模式 | 系统切到深色后，所有页面无白底闪现 |

**判据**：能写成「跑这个命令，看到这个输出」吗？写不出就说明它还不是验收标准。

## 一个反直觉的建议

> **spec 不是给 AI 看的说明书，是给你自己留的证据。**

半年后你（或另一个 AI）看到这段代码时，唯一能回答「为什么当时这么做」的，
就是这份 spec 里的「被否决的方案」和「非目标」。

**代码告诉你 What，spec 告诉你 Why。**
