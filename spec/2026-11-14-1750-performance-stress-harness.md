> **Status**: In Review
> **起始日期**：2026-11-14
> **预估工时**：150 分钟（单元累加）
> **对应提交**：（完成后回填）

## 背景 / 问题

2026-11-14 用户反馈「消息越多越卡」。排查发现根因是三层叠加：

1. `VStack`（非懒加载）把所有消息一次性布局且永不释放
2. `LazyVStack` 只延迟**创建**、不回收**已创建**的视图（换上去还引入滚动跳动）
3. `@Observable` 里每帧更新的时间戳 `lastLiveFrameAt` 触发全视图重绘

修完后**没有留下任何可复现的验证手段**——只能靠「用户觉得卡不卡」来判断。
这是不可接受的：**性能问题修完就必须变成可测量的基线**，否则下次改动会静默退化。

压测期间临时加的 `DSH_STRESS=N` 开关证明这条路可行（400 条消息 → 1.4 GB 复现），
但它只是草稿：只支持「消息条数」一个维度，且没有基线记录。

## 目标与非目标

**目标**
1. **一套固定压测场景**，用环境变量切换，`simctl launch` 就能跑，不需要真机、不需要连电脑。
2. **每个场景有内存基线**，写进仓库，改动后能对比。
3. **覆盖已知的高风险维度**：消息量、图片密度、过程步骤数、会话列表规模、复杂 Markdown。
4. 把「性能敏感改动要跑压测」写进规范，避免这次的经验变成一次性。

**非目标**
- 不做自动化性能回归 CI（模拟器内存读数在不同 Mac 上有波动，不适合卡硬阈值）。
- 不引入 Instruments/xctrace 等重工具链（太重，日常改动用不上）。
- 不压测网络层（延迟/弱网属于另一类问题，已有诊断报告的 `[ Live Signal ]` 覆盖）。

## 参考实现（Prior art）

- **Android 的 Macrobenchmark**：用固定场景 + 基线文件（`baseline-prof.txt`），
  CI 上对比耗时是否退化。
  → **采用**：场景固定 + 基线记录的思想。
  → **不采用**：完全不卡阈值。我们的场景跑在模拟器上，内存读数受宿主影响大，
  卡阈值会产生大量假失败；改为「记录基线 + 人工对比明显偏离」。
- **Web 的性能预算（performance budget）**：给关键指标设上限，超了就拒绝合并。
  → **部分采用**：只给「数量级」设上限（如滚动后内存不超过进会话的 1.5 倍），
  不给绝对值。数量级退化（87MB → 1.4GB）才是真问题。
- **Firebase Test Lab / XCTest 的 `measure {}`**：官方性能测量。
  → **不采用**：`measure` 适合算法级微基准，测不到「视图树膨胀」这类问题。

## 方案

### 第 1 步：把 `DSH_STRESS` 从「一个数字」升级成「场景列表」

现状：`DSH_STRESS=200` 只表示「200 轮消息」。

改为**场景语法**，支持逗号分隔多场景：

```bash
SIMCTL_CHILD_DSH_STRESS="messages:400,images:120" xcrun simctl launch <udid> <bundle>
```

| 场景 | 含义 | 用于验证 |
| --- | --- | --- |
| `messages:N` | N 轮「用户问 + 助手 Markdown 回复」 | 消息量（已有） |
| `images:N` | N 条消息，每条带一张图 | 图片解码 / 缩略图缓存 |
| `steps:N` | 每轮附带 N 个过程步骤 | 步骤渲染 / 展开成本 |
| `sessions:N` | N 个演示会话 | 列表规模 / 分组计算 |
| `markdown:extreme` | 每轮含 100 行表格 + 500 行代码块 | Textual 解析与布局 |

**为什么用环境变量而不是 UI 开关**：压测要能脚本化、能重复，
UI 开关每次都要手动点，无法在同一台机器上批量跑。

### 第 2 步：场景实现在 Debug 数据源

`ConnectionModel+Demo.swift` 已有 `stressMessages(rounds:)`，扩展成
`stressData(scenario:)`：

- 单个函数负责「按场景生成消息 + 步骤」
- 只在 `#if DEBUG` 编译
- 生产包零影响

### 第 3 步：基线表

在 `docs/architecture/performance-baseline.md` 记录每个场景的实测值：

| 场景 | 进会话 | 滚动一遍 | 说明 |
| --- | --- | --- | --- |
| `messages:400` | 87 MB | 399 MB | 硬裁剪 24 条后 |
| `images:120` | ? | ? | 待测 |
| `steps:80` | ? | ? | 待测 |
| `sessions:800` | ? | ? | 待测（列表页） |
| `markdown:extreme` | ? | ? | 待测 |

**基线不是阈值**，是「改动前后的对照物」。判断标准：
- **数量级变化**（87 MB → 300 MB）= 有问题，必须查
- **10-20% 波动** = 正常，忽略

### 第 4 步：一个脚本把场景跑一遍

```bash
./scripts/stress-run.sh messages:400 images:120 steps:80
```

脚本做：装最新 Debug 包 → 按场景启动 → 进会话 → 滚动 → 采样 RSS → 打印表。

**为什么要脚本**：手工跑五个场景要十几分钟且容易忘步骤，脚本化才是可回归的。

### 第 5 步：写进规范

- `ios架构设计规范.md` 加一节「性能压测」：什么改动要压、怎么压、基线在哪看
- `代码编写执行规范.md` 的提交清单加一条：**碰视图列表 / 图片 / Markdown 渲染的改动，提交前跑一次对应场景**

## 被否决的方案

| 方案 | 否决理由 | 否决依据 |
| --- | --- | --- |
| 只保留 `DSH_STRESS=N`（现状） | 只覆盖消息量一个维度；图片/步骤/列表的风险同样高 | 用户要求「分析还有哪些地方要压」 |
| 引入 Instruments CLI（`xctrace`）做自动采集 | 每次跑要几十秒且要解析 trace 文件，日常改动不会用 | 工具成本高于收益 |
| CI 卡硬阈值（如内存 > 200 MB 失败） | 模拟器内存读数受宿主负载影响，假失败会让人直接绕过这条检查 | 实测同一场景波动可达 20% |
| 用 XCUITest 自动滚动 | 要维护 UI 测试脚本，且滚动距离和帧率难以稳定测量 | 手工滚动 + 脚本采样 RSS 已足够定位数量级问题 |
| **不做压测** | 代价：这次 1.4 GB 的问题可能再次静默出现，只能等用户反馈 | 本次教训 |

## 代价与风险

**代价**（确定会付）
- 场景生成代码约 120 行（Debug only）
- 脚本约 80 行
- 基线表维护（每次性能改动要更新）

**风险**（可能发生）
| 风险 | 缓解 |
| --- | --- |
| 模拟器内存读数不稳定，基线漂移 | 只比数量级，不比绝对值；基线注明「同机同场景」 |
| 压测数据生成逻辑本身有 bug（如空消息） | 生成后先肉眼看一眼首屏 |
| 脚本在设备未连接时失败 | 脚本先检查 `devicectl list devices` |
| 场景过多导致没人跑 | 只保留 5 个核心场景，写进提交清单才有人用 |

**为什么不该做这件事**（诚实写反面）
- 性能压测是**给未来省时间**的事，短期看不到收益。
- 如果这个项目已经稳定、近期不改聊天界面，这套东西大部分时间不会被用到。
- 但考虑到这次问题是「用户先发现、我们后知道」，**把发现提前到提交前**这件事值得做。

## 未决问题（Unresolved Questions）

- 帧率要不要测？SwiftUI 没有公开的帧率读数，模拟器上也只能间接估计。
  本轮只测内存，帧率靠「用户体感 + Live Signal 的帧间隔」间接判断。
- 是否加 CPU 占用？`ps aux` 能给 %CPU 但毛刺很大，本轮不加。
- 冷启动时间算不算这套体系的一部分？本轮不作为压测场景（它是一次性指标），
  但建议单独记录一次基线。
