# App 内一键重启 DSH

> **文件名**：`spec/2026-11-16-0620-restart-from-app.md`
> **Status**：Draft（**2026-11-16 结论：当前架构下做不到优雅重启，见「架构事实」**）
> **起始日期**：2026-11-16
> **预估工时**：约 300 分钟
> **对应提交**：（未实现）

## 背景 / 问题

**现状**：插件代码、`package.json`、locale、图标、profile 配置**全部是启动时加载**的。
改任何一样都要重启 DSH 才生效，而重启只能**在电脑上操作**。

**这一轮实测的代价（2026-11-16）**：

为了验证 `dsh-plugin-panel` 的移动端路由，一共重启了 **5 次**：

| 次数 | 方式 | 结果 |
| --- | --- | --- |
| 1 | `setsid bash -c '...' &` | ❌ 失败：**macOS 没有 `setsid`** |
| 2 | `launchctl submit` + `osascript quit` | ❌ 失败：Electron 的 quit 弹确认框，后台无人点击 → `-128 用户已取消` |
| 3 | `launchctl submit` + `kill -9 57296` | ✅ 成功 |
| 4 | `launchctl submit` + 变量取空 PID | ❌ 失败：`kill -9` 空值，什么都没杀 |
| 5 | `launchctl submit` + `kill -9 98030`（父进程） | ✅ 成功 |

**用户原话**：

> 「我觉得重启这个功能本身不错哦，有的时候还真的用得上的，等之后把它做到我们这个产品中吧，比如增加一个重启的按钮。」

**典型场景**：

- 躺在床上用手机，发现某个插件的新功能没生效——**必须起身去电脑上重启**
- 在服务器上（无 GUI）改完插件，App 端却还是旧行为
- 插件作者迭代时，每改一次就要切到电脑

## 目标与非目标

**目标**

- **明确当前能力的边界**：为什么插件做不到优雅重启，以及用户该怎么做
- 把「需要重启的改动」尽可能变成「不需要重启」（优先做 `dsh.mobile` 这类声明）
- 若未来上游提供 restart 入口，App 侧能直接对接

**（原目标「服务端自 spawn 重启」已因架构事实撤销，见下节）**

**非目标**

- **不自动重启**（不做"检测到插件变化就重启"，太危险）
- **不做定时重启**
- **不做远程关机/启动**（DSH 停着的时候 App 连不上，这个功能天然做不到）
- **不改 DSH 内核**
- **不追求"无感重启"**——重启必然断会话，App 要做的是**把断会话讲清楚**

## 参考实现（Prior art）

**未找到直接参考。** 相关的两个模式：

- **VS Code 的 "Reload Window"**：`Cmd+Shift+P → Reload Window`，重载渲染进程但保留主进程。**不采用**——我们是 Electron **主进程 + host 子进程**两层，只重载 renderer 解决不了插件（插件在 host 层）。
- **`pm2 restart` / `systemd restart`**：外部守护负责拉起。**部分采用**——服务器场景确实应该走 systemd/launchd；但桌面端没有守护，必须能自重启。

**结论**：自重启（`spawn` 一个 detached 的自己再退出）是唯一在「无守护」前提下也能工作的方案。

## 架构事实（2026-11-16 实读 app.asar 确认）

**桌面端是两层进程**：

```
Electron 主进程（GUI，/Applications/.../Contents/MacOS/DeepSeek）
  ├── renderer（窗口）
  ├── helper（gpu / network / audio）
  └── host 子进程（Node.js，跑 DSH 核心 + 全部插件）
```

**插件跑在 host 子进程里**，不在主进程。

### 关键发现 1：host 任何退出方式都被判为失败

`lib/main.js:11840`（`child.once("close")`）：

```js
if (code !== 0 && code !== null) this.fail(`dsh desktop host exited with ${code}`);
else this.fail(`dsh desktop host stopped`);      // ← code=0 也 fail
```

**所以**：插件里调 `process.exit(0)` 和外部 `kill` **结果一样**——主进程都走 `fail()`，
弹恢复对话框。**「插件优雅退出自己」这条路不存在。**

### 关键发现 2：唯一优雅重启入口不可达

`lib/main.js:20092`（`DesktopFatalRecovery` 对象）：

```js
restart: () => {
    app.relaunch();              // Electron 官方优雅重启
    quitWithoutConfirmation();
}
```

**它只在两个地方被调用**：
- 崩溃恢复对话框的「重新启动」按钮（就是用户每次手点的那一个）
- 开发模式菜单的「Restart App Host」

**没有 IPC 暴露，插件够不到。** 插件在 host 子进程里，也拿不到 Electron 的 `app` 对象。

### 结论

> **「从插件内部安全重启 DSH 且不崩溃」在当前架构下做不到。**
> 任何 host 侧退出（`exit(0)` / `exit(1)` / 被 kill）都会让主进程进入恢复流程。

## 替代方案

### 方案 A：明确告知，不做远程重启（推荐）

App 里如果需要重启，**不提供远程重启按钮**，而是解释清楚：

```
「这个改动需要重启电脑上的 DSH。请在电脑上按 Cmd+Q 退出后重新打开。」
```

**为什么这样最好**：用户手动 `Cmd+Q` 是**唯一不产生崩溃恢复页**的路径
（Electron 自己走完整 quit 流程）。

### 方案 B：让需要重启的改动变成"不需要重启"

**这是真正有价值的方向**。分类看：

| 改动内容 | 能否不重启 | 现状 |
| --- | --- | --- |
| 插件的 `dsh.mobile` 声明 | ✅ **可以** | `/mobile/list` 每次请求重新扫 `node_modules`，已实现 |
| 插件的 locale / icon | ⚠️ 可能 | 需要在读取时重新读文件（未验证） |
| 插件的 JS 代码 | ❌ | HMR 默认 ignore `node_modules`，改 `ignored` 会把 DSH 搞坏（实测） |
| profile 配置 | ❌ | 启动时加载 |

**所以**：优先把「声明类」信息做成运行时读取，代码类改动老实重启。

### 方案 C：launchd 管理（不推荐）

注册 DSH 为 LaunchAgent，用 `launchctl kickstart -k` 重启。

**为什么否决**：桌面 App 被 launchd 接管后，Dock 行为、单实例、自动更新流程都可能出问题，
风险远大于收益，且只覆盖 macOS。

### 方案 D：给 DSH 上游提功能请求

请求暴露一个「restart」的 IPC/HTTP 入口（内部实现就是现有的 `app.relaunch()`）。
**这是唯一能让「App 内一键重启」真正干净落地的路径**，但取决于上游是否接受。

## 被否决的方案（Rationale & Alternatives）

| 方案 | 否决理由 | 依据 |
| --- | --- | --- |
| **只给「请在电脑上重启」的提示** | 不解决问题——用户在床上、在服务器前没有 GUI 时依然卡住 | 用户明确诉求 |
| **`osascript quit` + `open -a`** | Electron App 的 quit 会弹确认框，无人值守时被取消 | 实测 `-128 用户已取消` |
| **`launchctl kickstart`** | 桌面端 DSH 不在 launchd 管理下（手动打开） | `launchctl list` 里没有对应服务 |
| **依赖 systemd/launchd 守护** | 服务器场景可行，桌面端没有守护，覆盖不全 | 只能覆盖一半场景 |
| **热重载插件而不重启进程** | `dsh-hmr` 有 reload 能力，但**实测改插件后仍必须重启**；不可靠，不能作为产品能力 | 本轮 5 次重启全部必要 |
| **什么都不做** | 每次改插件都要手动去电脑前操作；本轮已消耗 5 次重启、其中 2 次失败 | 用户明确要求 |

## 代价与风险（Drawbacks & Risks）

**代价**（确定发生）

- **重启必然断会话**：正在跑的 Agent 任务会中断，必须二次确认
- 服务端多一个**能杀自己进程的端点**（虽然要 PIN，但仍是攻击面）
- App 侧要处理**重启前后的连接状态机**（重试、超时、失败提示）

**风险**

| 风险 | 缓解措施 |
| --- | --- |
| **重启后进程没起来**（`spawn` 失败 / 端口被占） | 端点先 `spawn` 成功再 `exit`；App 端最多轮询 20s 后明确报错而不是无限转圈 |
| **重启后端口变了，App 失联** | 文档要求固定端口；App 失败提示里明确写「端口可能变了，请重新扫码」 |
| **`detached` 子进程变孤儿**（父退出但子没正确接管） | `stdio: 'ignore'` + `unref()`；服务端日志记录 `self-respawn` 事件 |
| **误触重启** | 入口只在设置页（不在一级界面）+ 二次确认 + 文案写明后果 |
| **服务器上 `spawn` 的是 `node` 但原进程是 `dsh`** | 用 `process.execPath` + `process.argv.slice(1)`，保证和当前进程同样的启动方式 |

**为什么不该做这件事**（诚实）

- **重启是"编辑器思维"，不是"产品思维"**——好的产品不该让用户知道"要重启"；
- 真正的解法是**让插件支持可靠热重载**，那才是根治；
- 这个功能本质是**给一个架构缺陷补一个按钮**。

**但它值得做**：因为热重载不是短期能解决的，而**用户每天都会撞上"改了没生效"**。

## 未决问题（Unresolved Questions）

- **服务器场景要不要走 systemd 重启？** 如果检测到 `INVOCATION_ID`（systemd 环境变量），可以 `systemctl restart` 而不是自 spawn。**倾向**：v1 统一走自 spawn，v2 再分场景。
- **重启前要不要落盘未完成的会话状态？** DSH 本身有持久化，但**正在跑的一轮**会丢。**倾向**：文案里明确写"正在跑的任务会中断"，不做额外保存。
- **App 端重连用哪个地址？** 如果端口变了，旧地址无效。**倾向**：v1 只重试旧地址，失败就给明确指引。
- **要不要限制重启频率？** 防止某个 bug 导致无限重启循环。**倾向**：服务端记录 1 分钟内重启次数，超过 3 次拒绝并报错。
