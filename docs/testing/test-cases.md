# 测试用例库

> **这份文件是骨架，不是完成品。**
>
> 用例**不要求一次填满**——先把场景位置站住，未来开发遇到新情况就往对应格子里填。
> 下次构造类似用例时，至少知道「这一类问题别人测过什么」。
>
> 加用例的判据：**下次改到同一块代码时，你会想再跑一次它**。
> 跑完就丢的临时验证，写在 spec 或提交信息里，不要进这个文件。

## 1. 渲染层

### 1.1 消息列表 ✅ 已覆盖

| 用例 | 怎么跑 | 验证点 | 基线 |
| --- | --- | --- | --- |
| 长会话内存 | `./scripts/stress-run.sh messages:400` | 稳定 RSS 不超基线数量级 | 400 MB |
| 硬裁剪 | 开 400 条会话，往上滑到头 | 只保留最近 24 条，`hasMore` 变 no | — |
| 滚动流畅 | 400 条会话连续上下滑 | 无跳动、无重叠 | — |
| 大量会话 | `./scripts/stress-run.sh sessions:800` | 列表可滚动、分组正确 | 277 MB |

**已验证的坑**：
- `LazyVStack` 不回收已创建视图（滚动 1.4 GB）；缓存行高导致跳动
- `List` **能回收**（400 轮 389 MB），但在本项目的结构里**滚不动**——3 个变体全试过：
  原始 / 移除 `defaultScrollAnchor` / 加 `fixedSize`，模拟器截图哈希完全一致（零位移）
- **结论**：`VStack` + 数据层限制条数（30 条）

**换列表容器时必须测三件事**：①能不能滚 ②滚动跳不跳 ③内存。
只测内存会得出「List 很好」的错误结论（踩过）。

**最近一次实测**（2026-11-14，模拟器）：
```
空载（连接页）          281 MB
会话列表（5 个会话）     320 MB
进会话（24 条）         343 MB
长会话 400 轮           397 MB（日志：丢弃 776 条 / 保留 24 条）
图片 60 张              307 MB
```

**真机验证**（2026-11-14，`TEST-RENDER-001`，185 行代码块 + 8 列 18 行表格）：
- 代码块正常显示，**无配色**（符合设计）
- 表格正常，不挤
- 滚动不卡顿
- 无闪退

## 2. 数据层

### 2.1 消息合并与顺序 ✅ 已覆盖

| 用例 | 怎么跑 | 验证点 |
| --- | --- | --- |
| 连发顺序 | `DSH_SEND_BURST=5` | 5 条全送达、时间戳递增 |
| pending 确认 | 发送后看气泡状态 | 从「待发」变「已送达」，不重复 |

**已验证的坑**：`isSending` 时发送函数直接 return，配合按钮不禁用 → 静默丢消息。
**结论**：互斥锁和 UI 禁用必须成对出现。

### 2.2 裁剪边界 ⬜ 待填

**未来要测**：
- 正好 24 / 25 条时裁剪是否正确
- 裁剪时 pending 消息是否被误删
- 裁剪后 `hasMore` 状态
- 裁剪后滚动位置是否跳变

### 2.3 多端并发 ⬜ 待填

**已知设计**：以服务端 `sequence` 为唯一权威（手机/电脑时钟不可信）。
**未来要测**：
- 手机和电脑 1 秒内各发一条，顺序是否以服务端为准
- 本地 pending 被服务端消息「顶下去」时的视觉跳变

### 2.4 断网补发 ⬜ 待填

**未来要测**：
- 断网发 3 条 → 联网后是否按序全部发出
- 断网期间切换会话，消息是否留在原会话
- 补发失败重试次数与最终失败提示

### 2.5 数据持久化 ⬜ 待填

**未来要测**：
- 杀进程重启后草稿是否恢复
- 草稿图片是否恢复（磁盘配额）
- outbox 重启后是否继续投递

### 4.2b 问答卡（ask_user_question）✅ 已覆盖

| 用例 | 怎么跑 | 验证点 |
| --- | --- | --- |
| 手机端回答 | 电脑端触发 ask_user_question，手机选一项提交 | **agent 当场收到答案**；卡片收起；不出现「回答没被接受」 |
| 通道就绪 | 启动后看诊断 | 出现「问答通道就绪 clientId=…」 |
| 完整链路 | 回答后看诊断 | 「收到请求 method=user-questions/request」+「已回传结果」 |
| 电脑端同时开着 | 浏览器和 App 都显示卡片 | 任一端答了之后另一端应收到 cancel，不再重复提交 |

**已验证（2026-11-14 真机）**：
```
问答通道就绪 clientId=b04b5fd2
问答通道收到请求 method=user-questions/request eventId=ecdfea9b-644
问答通道已回传结果：eventId=ecdfea9b-644
```

**踩过的坑**：早期走 `userQuestions/answer`，服务端要求问题处于 `continued` 状态，
而该状态只在工具超时（120 秒）后出现——所以点必然被拒（`value: false`）。
**正确路径是 `$events` 通道回传**，见坑记录第 12 条。

## 怎么加新用例

**格式**（三层都要写）：

| 项 | 说明 | 反例 |
| --- | --- | --- |
| **怎么跑** | 命令、环境变量、或具体操作步骤 | 「打开会话」 |
| **验证点** | 可观察的状态 | 「渲染正常」 |
| **基线** | 数字，没有就写 — | 「应该不卡」 |

**正例**：「发送中再点发送按钮 → 按钮置灰，点不了」——能执行、能判断。
**反例**：「验证发送功能正常」——没法执行、没法判断通过。

**新场景怎么落位**：
1. 先判断属于哪一层（渲染/数据/网络/交互/启动）
2. 再看那层下面有没有对应子类，有就填进去
3. 没有就新建一个 `X.N 子类 ⬜ 待填`，写清楚「未来要测什么」
4. 填了就把 ⬜ 改成 ✅，补上「怎么跑 / 验证点 / 基线」
