# 性能压测基线

> 用 `./scripts/stress-run.sh <场景>` 采集。
> **基线不是阈值**——只比数量级，不比绝对值。模拟器内存读数受宿主负载影响，实测波动可达 20%。
>
> 判断标准：**数量级变化**（如 400 → 1200 MB）= 有问题必须查；10–20% 波动 = 正常。

## 采集环境

| 项 | 值 |
| --- | --- |
| 日期 | 2026-11-14 |
| 设备 | 模拟器 DSH Pocket Max（iPhone 17 Pro Max, iOS 26.3） |
| 构建 | Debug |
| 测量 | 进会话后稳定 RSS（连续采样 4 次取最后值） |
| 空载基线 | **281 MB**（连接页，无会话） |

## 当前基线

| 场景 | 稳定 RSS | 相对空载 | 说明 |
| --- | --- | --- | --- |
| 空载（连接页） | 281 MB | — | 框架 + Debug 构建的基础开销 |
| `messages:400` | **400 MB** | +119 MB | 800 条消息，硬裁到 24 条后 |
| `images:120` | **307 MB** | +26 MB | 240 条消息全带图，裁到 24 条 |
| `steps:80` | **319 MB** | +38 MB | 每轮 80 个步骤 |
| `markdown:extreme` | **527 MB** | **+246 MB** | 100 行 × 8 列表格 + 500 行代码块 |
| `sessions:800` | **277 MB** | — | 列表页，800 个会话 |

## 结论

**最大风险是极端 Markdown**（+246 MB）——100 行表格 + 500 行代码块的布局成本远高于消息数量本身。

**图片和步骤的影响很小**（+26 / +38 MB），因为硬裁剪把消息数压到了 24 条，
图片全屏和步骤展开的峰值需要单独测（不在本基线内）。

## 已知未覆盖

| 场景 | 为什么不测 | 建议 |
| --- | --- | --- |
| 全屏图片翻页 | 需要 UI 交互，脚本采不到瞬时峰值 | 手工 + `ios_sim_*` 工具 |
| 步骤全部展开 | 需要点开每一组 | 用 `DSH_EXPAND_STEPS=1`（已有开关）单独跑 |
| 实时流高频更新 | 需要连真机或模拟流 | 真机上看 `[ Live Signal ]` 的帧率 |
| 冷启动时间 | 一次性指标，不属于稳态压测 | 单独记录一次 |

## 怎么更新这张表

1. 改完性能敏感代码（列表/图片/Markdown 渲染）
2. 跑对应场景：`./scripts/stress-run.sh messages:400`
3. 对比上表：
   - 数量级变化 → 查原因，不要提交
   - 20% 内波动 → 直接更新这行数字
4. 如果有新场景，加到脚本和这张表里
